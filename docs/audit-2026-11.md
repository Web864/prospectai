# Audit report — November 2026

Scope: web app, API, queue, crawler, worker, database migrations, Chrome extension.
Method: ran format, lint, typecheck and all tests; applied all 6 migrations to a clean PostgreSQL 16;
reproduced concurrency behaviour against a real database; probed the SSRF guard with adversarial
inputs; read the authorization layer route by route; read the extension's auth, storage and API code.

## Fixed in this branch

| #   | Area           | Problem                                                                                                                                                                                                                                                                                                       | Fix                                                                                                                                                                                                                                  |
| --- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Queue / quotas | Usage reservations ran at SERIALIZABLE. The snapshot is taken at the advisory-lock statement, so every waiter hit a stale-snapshot serialization error (P2034) and the web routes returned 500. Reproduced on PostgreSQL 16: 6 of 8 concurrent submissions failed.                                            | Run reservations at READ COMMITTED; the per-organization advisory lock already guarantees mutual exclusion. Verified: all distinct requests succeed, duplicate idempotency keys replay one job, a quota of 3 admits exactly 3 of 10. |
| 2   | Crawler / SSRF | `isPrivateIpv6` compared raw strings, so equivalent spellings (`0:0:0:0:0:0:0:1`) bypassed it; IPv6 URL literals skipped the explicit check (bracketed host); public IPv6 literals were wrongly rejected; Teredo, 6to4-embedded private IPv4, site-local and several deprecated IPv4 ranges were not blocked. | Canonicalize before numeric CIDR checks, strip URL brackets, extend the blocklist.                                                                                                                                                   |
| 3   | API errors     | Unexpected errors were never logged; malformed JSON returned 500; transient database failures returned a generic 500.                                                                                                                                                                                         | Structured logging with request id; 400 for bad JSON; retryable 503 + `Retry-After` for transient database errors.                                                                                                                   |
| 4   | Extension      | The server issues a 60-minute access token and a 30-day rotating refresh token, but the extension never used the refresh token, so signed-in users saw "Session expired" every hour.                                                                                                                          | Proactive and reactive refresh, serialized across popup and service worker with the Web Locks API (rotating refresh tokens are single-use). Popup no longer resets mid-analysis on a silent refresh.                                 |
| 5   | Repo hygiene   | A generated `tsconfig.tsbuildinfo` was tracked.                                                                                                                                                                                                                                                               | Untracked and ignored.                                                                                                                                                                                                               |

30+ regression tests were added. The queue test and the refresh concurrency test were each verified to
fail when the fix is removed.

## Reviewed and found sound

- Authorization: every route is gated by `requireRequestActor` or is intentionally public (login, signup,
  OAuth, health, token exchange); queries are scoped to the caller's organization; the admin route requires
  the owner role.
- Session cookie is HttpOnly, SameSite=Lax.
- Database schema: strong CHECK constraints, partial claim index, unique idempotency key; all migrations
  apply cleanly from empty.
- Extension: PKCE and `state` verified, minimal permissions (`identity` is used), strict extension-page CSP,
  HTTPS-only production URLs.

## Open items (not changed)

1. **No Content-Security-Policy or HSTS headers** on the web app. Add deliberately and test against real pages.
2. **No database-backed integration test in CI** for queue concurrency. A real-PostgreSQL test would stop
   bug 1 from returning.
3. **Refresh-token loss window.** If a refresh response is lost after the server rotates the token (for
   example the service worker is killed mid-request), the user must sign in again. A short server-side grace
   window for the previous refresh token would close this.
4. **No rate limit on `/extension/refresh`.**
5. **Extension popup (`popup-app.tsx`, ~700 lines)** was only reviewed where it touches sign-in; polling,
   cancellation and screen logic were not audited.
6. **Not exercised:** the app was not run end to end in a browser, and the extension was not loaded into
   Chrome against a live server. The Prisma engine could not be downloaded in the audit sandbox, so the
   queue SQL was verified directly against PostgreSQL rather than through Prisma.
